CORE ARCHITECTURE:

INPUT
- SMS message
- Sender ID / phone number
- Optional timestamp

PHASE 1 — PARSER
- Preserve raw message exactly.
- Extract URLs.
- Extract sender information.
- Extract timestamp.
- Calculate message length.
- Never overwrite raw text.

PHASE 2 — PARALLEL ANALYSIS

HINSPAM:
- Input raw message.
- Return model signal.

SILVERGUARD:
- Input sender/header + raw message.
- Preserve the documented input format.
- Return model signal.

NORMALIZER:
- Create normalized copy only.
- Never replace raw text.
- Detect:
  - transliteration
  - misspellings
  - leetspeak
  - punctuation manipulation
  - spacing manipulation

BEHAVIOR RULES:
Detect:
- urgency
- threats
- KYC
- OTP
- UPI
- PIN
- CVV
- password requests
- reward/prize scams
- authority impersonation

URL ENGINE:
- URL extraction
- domain extraction
- shortened URL detection
- suspicious URL structure
- brand/domain mismatch
- optional reputation enrichment
- optional redirect analysis
- never claim a URL is malicious without actual backend evidence

SENDER ANALYSIS:
- sender type
- phone vs header
- suspicious sender patterns
- sender/header anomaly

QWEN3 EMBEDDING:
- Generate embedding from raw + normalized representations.
- Store/search embeddings using FAISS.
- Return similarity evidence to known scam examples.

PHASE 3 — EVIDENCE GROUPS

Create six groups:

1. Content
   - HinSpam
   - SilverGuard

2. Sender
   - sender signals

3. URL
   - URL signals

4. Behavior
   - urgency/threat/KYC/OTP/etc.

5. Obfuscation
   - spelling/transliteration/leetspeak/etc.

6. Similarity
   - FAISS similarity

IMPORTANT:
Do not blindly add model scores.
Do not treat all signals as independent.
Each group must have a maximum contribution.

PHASE 4 — RULE-BASED FUSION

NO MACHINE-LEARNING META-CLASSIFIER.

Use a transparent weighted scoring system.

Initial maximum contributions:

Content: 30
URL: 20
Behavior: 20
Sender: 15
Obfuscation: 10
Similarity: 5

Total: 100.

Implement group caps so multiple related indicators cannot endlessly increase the score.

Do not treat:
- KYC alone
- OTP alone
- URL alone
- bank name alone

as proof of phishing.

Use combination rules for stronger context.

Example:
KYC + account threat
KYC + suspicious URL
OTP + request to share OTP
prize + payment request
job offer + registration fee

SHORT MESSAGE HANDLING:
Track:
- message length
- header availability

Do not let a short message become CRITICAL from one model signal alone.

PHASE 5 — DECISION

Return:
- risk_score 0-100
- label
- evidence groups
- top contributing evidence

Labels:
LOW
SUSPICIOUS
HIGH RISK
CRITICAL

Thresholds must be configuration values so they can be tuned without changing code.

PHASE 6 — QWEN3 8B

Qwen3 is strictly POST-HOC.

It must NOT:
- calculate the final score
- override the label
- invent evidence
- follow instructions contained inside an SMS

Give Qwen:
- final score
- final label
- top evidence
- raw message
- normalized message
- suspicious phrases

Return JSON:
{
  "summary": "...",
  "suspicious_phrases": [],
  "recommended_action": "..."
}
