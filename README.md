# SMSense

## AI-Powered SMS Threat Intelligence for Indian SMS, Smishing & Vernacular Phishing

SMSense is a cybersecurity platform designed to analyze SMS messages for phishing, smishing, scam, social-engineering, and obfuscation indicators, with particular attention to Indian English, Hindi, and Roman-Hinglish messages.

The project combines **pretrained machine-learning models**, **rule-based security analysis**, **URL intelligence**, **sender analysis**, **obfuscation detection**, **semantic similarity search**, and an **LLM explanation layer** into one explainable analysis pipeline.

> **Important:** SMSense's final security decision is generated by an interpretable rule-based evidence-fusion engine. Qwen3 is used for post-hoc explanation only and does not override the security score or label.

## What is SMSense?

SMSense is an AI-assisted SMS security analysis platform focused on identifying suspicious messages before a user interacts with them.

It is designed around a practical problem: modern phishing and smishing messages often use:

- Urgency and account threats
- KYC/account verification themes
- OTP and credential requests
- UPI/PIN/CVV/password requests
- Reward, lottery, cashback, or job scams
- Suspicious URLs and shortened links
- Sender/header anomalies
- Intentional spelling changes
- Leetspeak and character substitutions
- Roman-Hinglish and vernacular language
- Minor message changes designed to evade simple keyword matching

SMSense does not rely on one classifier. Instead, it collects evidence from multiple independent analysis paths and combines that evidence into an explainable score.

---

## Problem

SMS phishing (smishing) remains effective because users often receive short, conversational, and highly localized messages. Indian users may receive messages in English, Hindi, Roman-Hinglish, or mixed forms, and scam messages can deliberately manipulate spelling to evade simple filters.

Traditional keyword-only filtering can fail when:

```text
KYC update karo warna account block hoga
```

is transformed into:

```text
KYC upd8 kro warna acc0unt blck hoga
```

At the same time, a legitimate security message can contain words such as `OTP`, `login`, `account`, or `verify` without being malicious:

```text
Your OTP for login is 4821. Do not share it with anyone.
```

SMSense therefore needs to distinguish between:

- **Security vocabulary** and **actual malicious intent**
- **Normal messages** and **social-engineering combinations**
- **Clean text** and **obfuscated variants**
- **Model evidence** and **final security decisions**

---

## Solution

SMSense uses a parallel evidence architecture.

```text
                    SMS / Message
                         |
                         v
                 Structured Parser
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
      Content         Behavior         URL
      Analysis        Analysis       Analysis
          |              |              |
      SMS-Shield     Rule Engine    URL Rules
          |              |
          +------+-------+--------------+
                 |
                 v
        Sender + Obfuscation
                 |
        Qwen3 Embedding + FAISS
                 |
                 v
        Evidence Fusion Engine
                 |
                 v
           Risk Score 0-100
                 |
                 v
     LOW / SUSPICIOUS / HIGH RISK / CRITICAL
                 |
                 v
              Qwen3 8B
                 |
                 v
        Post-Hoc Explanation
```

Every detector remains independent. The frontend never implements the security decision itself; the FastAPI backend is authoritative.

## Key Features

### 1. SMS Analysis

Analyze a message with:

- Message body
- Sender/header/phone number
- Optional timestamp

The result includes:

- Risk score
- Risk label
- Scam category
- Language hint
- Raw message
- Normalized message
- Suspicious phrases
- Evidence breakdown
- URL intelligence
- Obfuscation analysis
- Model signals
- Human-readable explanation
- Recommended action

### 2. Vernacular / Hinglish Support

SMSense recognizes Roman-Hinglish indicators and can distinguish them from normal English text.

Example:

```text
KYC upd8 kro warna account blck hoga
```

is identified as Hinglish rather than English.

A message such as:

```text
Your OTP for login is 4821. Do not share it with anyone.
```

is identified as English.

### 3. Obfuscation Detection

The system detects:

- Leetspeak
- Misspellings
- Transliteration
- Punctuation manipulation
- Spacing manipulation
- Repeated characters
- Concatenated/split patterns
- Spelling normalization

Example:

```text
upd8  -> update
blck  -> block
acc0unt -> account
```

### 4. Behavior / Social Engineering Detection

Detects patterns related to:

- Urgency
- Threats
- KYC
- OTP
- UPI
- PIN
- CVV
- Passwords
- Rewards/prizes
- Authority impersonation themes
- Credential requests

The engine also recognizes combinations such as:

- KYC + account threat
- KYC + urgency
- KYC + URL
- OTP + credential request
- Reward + payment request
- Job offer + fee

### 5. URL Intelligence

For URLs found in an SMS, SMSense can inspect structural indicators such as:

- Shortened URLs
- Suspicious URL structure
- IP-address URLs
- Brand/domain mismatch
- Domain information returned by the backend
- Reputation state when supplied by the backend

SMSense does **not** claim a URL is malicious merely because a structural indicator exists. URL reputation is optional and disabled until `GOOGLE_SAFE_BROWSING_API_KEY` is configured in `artifacts/api-server/.env`. When enabled, only extracted URL strings are sent to Google; the complete SMS and sender are not sent. A URL itself may contain sensitive query parameters, so enable external lookups only when that disclosure is acceptable. A no-match result is not a guarantee that a URL is safe. See the [backend setup guide](artifacts/api-server/README.md#optional-url-reputation).

### 6. Sender Analysis

The sender path considers:

- Phone vs. SMS header format
- Sender structure
- Promotional-looking patterns
- Unusual sender characteristics

A sender claiming to be a brand such as `SBI` is not automatically treated as malicious. Sender evidence requires actual anomaly evidence.

### 7. Semantic Similarity

SMSense can embed the message using:

```text
Qwen3 Embedding 0.6B
```

and search a local FAISS index of scam-example vectors.

Similarity is treated as supporting evidence only. It is **not** interpreted as a phishing probability.

### 8. Explainable Risk Fusion

The final score is produced by a rule-based evidence-fusion engine with explicit category caps. This makes the score auditable and easy to explain during a security review or hackathon demonstration.

### 9. Post-Hoc AI Explanation

Qwen3 8B receives the already-determined security result and generates:

- Human-readable summary
- Suspicious phrases
- Recommended user action

Qwen3 does not determine the final label.

### 10. Adversarial Testing

The frontend can compare original and modified messages to demonstrate robustness against:

- Spelling mutations
- Leetspeak
- Punctuation changes
- Spacing changes
- Vernacular/Roman-Hinglish variations

## How SMSense Works

A message passes through several stages.

### Phase 1 — Ingest and Parse

Input:

```text
Message + Sender + Timestamp
```

The parser extracts:

- Raw message
- Sender
- Timestamp
- URLs
- Domains
- Message length

The raw message is preserved exactly.

### Phase 2 — Parallel Evidence Extraction

Multiple detectors run independently.

#### Content

SMS-Shield is the primary pretrained content classifier; its output is treated as capped evidence, not as a calibrated probability.

#### Behavior

Rule-based social-engineering indicators.

#### URL

URL structural analysis.

#### Sender

Sender/header structure analysis.

#### Obfuscation

Normalization, leetspeak, misspelling, transliteration, spacing, punctuation, and related transformations.

#### Similarity

Qwen3 embedding + FAISS nearest-neighbor evidence.

### Phase 3 — Evidence Fusion

The engine converts these signals into six evidence categories and caps each category.

### Phase 4 — Final Risk Score

The evidence values are summed into a 0–100 score.

### Phase 5 — Labeling

The score is mapped into a severity label.

### Phase 6 — Explanation

Qwen3 8B produces a human-readable explanation from the final result and returned evidence.

### Phase 7 — Persistence and UI

The backend stores the completed analysis in SQLite so it can appear in History and Dashboard views.

## Evidence Categories

SMSense uses six final evidence categories.

| Evidence Category | Maximum Contribution | Purpose |
|---|---:|---|
| Content | 30 | Pretrained model/content evidence |
| Sender | 15 | Sender/header anomalies |
| URL | 20 | URL structural evidence |
| Behavior | 20 | Social-engineering and credential-request behavior |
| Obfuscation | 10 | Spelling, leetspeak, transliteration, manipulation |
| Similarity | 5 | Semantic similarity to local scam examples |
| **Total** | **100** | **Maximum evidence score** |

These caps are intentionally visible in the API response and frontend.

---

## Risk Scoring

The final score is an **evidence-based risk score**, not a calibrated probability.

Do not interpret:

```text
37 / 100
```

as:

```text
37% probability of phishing
```

It means that the combined evidence reached a score of 37 under the current rule set.

The severity labels used by SMSense are:

```text
LOW
SUSPICIOUS
HIGH RISK
CRITICAL
```

The exact thresholds are configurable in the backend configuration.

## Rule-Based Behavior Analysis

SMSense deliberately avoids using a single keyword as proof of maliciousness.

For example:

```text
OTP
```

by itself does not create a meaningful phishing score.

But:

```text
Send me your OTP
```

creates a credential-request signal and a stronger combination signal.

Similarly:

```text
KYC
```

alone is not treated as sufficient proof.

But:

```text
KYC + account threat + urgency
```

creates stronger behavioral evidence.

This reduces common false positives caused by security-related words appearing in legitimate messages.

---

## Vernacular and Obfuscation Detection

SMSense is designed for messages that mix Indian-language vocabulary with Latin characters.

Examples:

```text
KYC karo
KYC kro
KYC upd8 kro
warna account block hoga
abhi verify karo
OTP bhejo
```

The normalization layer also helps expose variants such as:

```text
upd8      -> update
acc0unt    -> account
blck       -> block
```

The system preserves both versions:

```text
RAW
KYC upd8 kro warna account blck hoga

NORMALIZED
kyc update kro warna account block hoga
```

This allows the frontend to explain what transformation or obfuscation was detected instead of hiding it.

The URL engine currently focuses on structural evidence.

Example fields include:

```text

```

```text

```

## Sender Analysis

Sender evidence is deliberately conservative.

Examples:

```text
SBI
VM-SBIHELP
+919876543210
```

The system does not treat the presence of a bank or brand name as proof of compromise or spoofing.

Actual sender anomalies can contribute evidence; ordinary sender formatting does not automatically generate a high risk score.

## Semantic Similarity and FAISS

SMSense uses:

```text
Ollama
Qwen3 Embedding 0.6B
FAISS CPU
```

Current local demo index characteristics:

```text
Vectors:   3 scam-example vectors
Dimension: 1024
Metric:    L2
```

The similarity stage performs nearest-neighbor search and returns evidence such as distances to known scam examples.

Similarity is intentionally capped at **5 points** and is not presented as a probability.

A semantic match alone should not be enough to label a message malicious.

## Current Pretrained Models

SMSense uses one primary pretrained SMS classifier and separate models for optional explanation and semantic retrieval. It does not combine every installed model into the final score.

### SMS-Shield — primary detector

Configured Ollama model:

```text
hf.co/ganmoor-ai-labs/sms-shield:Q4_K_M
```

SMS-Shield targets Indian SMS, including English, Hindi and Roman-Hinglish. Its structured risk output is one evidence source, capped at 30 points in the current fusion engine. The model score is not a calibrated probability. Its publisher's model-card metrics are not independently verified SMSense metrics.

### Qwen3 Embedding 0.6B — semantic retrieval

Configured Ollama model:

```text
qwen3-embedding:0.6b
```

This generates message embeddings for a local FAISS nearest-neighbor search. The current bundled seed corpus has only three examples and is demo data. Similarity is supporting evidence only and is capped at five points.

### Qwen3 8B — optional explanation

Configured Ollama model:

```text
qwen3:8b
```

This generates a post-hoc explanation and recommended action after the score and label are computed. It cannot override the detection decision. If explanation generation fails, the detection result is retained.

### IndicBERT — optional diagnostic challenger

The optional model `anmolshrivastav/indicbert-scam-classifier-v2` is disabled by default. It requires the optional ML dependencies and reports a diagnostic signal only; it does not participate in production fusion.

HinSpam and SilverGuard are not part of the current primary scoring pipeline. Use the backend README and `MODEL_EVALUATION.md` as the source of truth for current model configuration and evaluation limitations.

## Qwen3 Explanation Layer

The security decision is already available before Qwen3 is called.

Conceptually:

```text
Evidence
   |
   v
Rule-Based Fusion
   |
   v
Final Score + Label
   |
   v
Qwen3 8B
   |
   v
Explanation Only
```

This prevents an LLM from overriding the deterministic security result.

The frontend displays:

- Summary
- Suspicious phrases
- Recommended action

as `post_hoc` information.

Each result can be examined using the same detailed evidence view used for new analysis.

## Security Design Principles

### Explainability

The final score is decomposed into visible evidence categories.

### No Black-Box Meta-Classifier

SMSense does not train a custom fusion model for the final score. The final decision is produced with explicitly defined evidence rules and caps.

### LLM Containment

Qwen3 is not allowed to override the security decision.

### Fail-Closed Model Availability

When required models are unavailable, the backend can return a model-unavailable error instead of fabricating a security result.

### Separation of Responsibilities

```text
Frontend
    -> display + input

FastAPI
    -> analysis orchestration

Models / Rules
    -> evidence

Fusion
    -> final score + label

Qwen3
    -> explanation only
```

### Raw Message Preservation

The original input is retained separately from normalized text so analysis remains auditable.

## Limitations

SMSense is a prototype and should not be treated as a complete enterprise-grade anti-phishing gateway.

Current limitations include:

- The semantic index is currently a small local demo corpus.
- Similarity is supporting evidence, not a calibrated probability.
- URL reputation/redirect intelligence depends on what the backend actually checks; `not_checked` is not treated as malicious.
- Rule-based language detection is a lightweight hint, not a comprehensive language-identification system.
- Pretrained model behavior depends on the models and their original training distributions.
- Model outputs can disagree.
- The final 0–100 score is an interpretable evidence score rather than a statistically calibrated probability.
- Performance on a local machine depends heavily on CPU/RAM and local model inference speed.
- The prototype does not claim that every detected threat is confirmed malicious.
